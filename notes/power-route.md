# 电源菜单路线（2026-10-27 起）

用户明确要求（2026-10-27）：`#/power` = **打开电源菜单**，只开不关 ✓。

- **段位** ✓：`#/power`（无身份 ✓，一个应用只有一个菜单 ✓）。
- **反映** ✓：`powerMenuOpenOf()` —— 契约属性 `data-dsh-power-menu`（值 `open` ✓ 或空 ✓）优先 ✓，其次是这个插件的 `.dshpm-menu` / `.dshpm-trigger[aria-expanded="true"]`（`getElementsByClassName` ✓，假 DOM 没有就跳过 ✓）。菜单开着时 canonical **就是它** ✓（盖在所有表面之上 ✓），关掉后自动回到底下那个界面 ✓。
- **驱动** ✓：点 `.dshpm-trigger`（或 `data-dsh-power-trigger`）**一次** ✓；**已经开着就不点** ✗ —— 它是开关 ✓，重试循环会把菜单开了又关（与模型页卡片同一个陷阱 ✓）。
- **动作段：`#/power/shutdown` / `#/power/restart`** ✓（2026-10-29 用户明确要求 ✓）。**动作是命令，不是地方** ✓ —— 所以它有一条**全仓唯一的来源闸** ✓：只认**读者亲手敲进地址栏**的 fragment ✓（`typedClaim` ✓，由 `driveTypedFragment` 升旗 ✓、**每一次 hash 读都降旗** ✓）→ 聊天消息 / README / **AI 回复**里的链接点了**不会关掉应用** ✓（用例 `a power action that arrives as a hash change is not run` ✓）。**一次 claim 只发一次** ✓（`powerActionSent` ✓，`dropLink` 复位 ✓）；**boot 的 hash 不触发** ✓（boot 走 `safeReadLink` ✗ 不是 typed ✓）→ 重启后残留的 `#/power/shutdown` 不会变成重启循环 ✓。
- **动作的 id 必须能过 canonical** ✓（2026-10-29 自己踩到 ✓）：`routeHash('power', …)` 原来**无条件**返回 `#/power` ✗ → 地址栏拿"规范化后的 wanted"（= 裸 `#/power` ✗）去和屏幕比 ✗ → 一条**已经发出**的命令被判「打不开」✓。现在 `routeHash` 保留动作段 ✓（`#/power/restart` ✓），并且 `arrived()` **先**判"这是不是一条命令" ✓（是就直接算落地 ✓）—— 因为屏幕上永远不会有东西等于一条命令 ✓（应用正在退出 ✓）。
- **先走它自己的 UI，端点只做兜底** ✓（2026-10-29 用户要求 ✓）：`#/power/<动作>` 的驱动是**两级** ✓ —— ① 开它自己的菜单 ✓ → 点它发布的**那一项** ✓；② **菜单给 `POWER_ACTION_MENU_LIMIT = 4` 次驱动机会**（≈2 秒 ✓）都没交出那一项 → 走端点 ✓。这样它的流程会跑 ✓（它自己的遮罩 ✓，将来它若加二次确认也会经过 ✓），而且**永远不会静默 no-op** ✓（这是最重要的性质 ✓）。
- **绝不按标签点不可逆的项** ✗（2026-10-29 血的教训 ✓）：`dsh-power-menu-mac` 的两项只有标签 `关闭DSH` / `重启DSH` ✓，**差一个字** ✗ —— 用户报"`#/power/restart` 激活的是关闭" ✓。猜标签点一个**会结束应用**的按钮，猜错不可恢复 ✗ → **只认契约属性** ✓（`data-dsh-power-action="<动作>"` ✓，限定在 `powerMenuOf()` = `[data-dshpm-menu]` ✓ 或 `.dshpm-menu` ✓ 里 ✓），**没有契约属性就整条走端点** ✓ —— 端点 URL 里带着动作名 ✓，**结构上不可能串** ✓。要给 A 路径加契约：给它的两个 `MenuItem` 各加一行 `'data-dsh-power-action': 'shutdown' | 'restart'` ✓。
- **焦点：真机制在插件那边，修法也在那边** ✓（2026-10-29 ✓）：`dsh-power-menu-mac` 原来有个 `useEffect(…, [open])` 在菜单打开时调 **`first.focus()`** ✓ —— 那是**「关闭DSH」** ✗，读者的地址栏**失焦** ✗，他**再按一次 Enter**（以为没反应 ✓）就由浏览器**原生激活焦点上的按钮** ✓ → **关闭** ✓。日志佐证 ✓：`warnings: []` ✓（我们两条路都会先写一行 ✓，一行都没有 ✓ → **不是我们点的** ✓），`attempts.inner` 停在 2 ✓（我们没走到动作 ✓）。
  ⇒ **我们在自己这边抢过一次焦点，撤了** ✗：`.35` 里 `openPowerMenu()` 之后调 `host.focusAddressBar()` ✓ —— 插件那边改好之后（删掉 `first.focus()` ✓、把 `onKeyDown` 挂到**触发按钮**上 ✓、开菜单时 `triggerRef.current?.focus()` ✓），**再抢就会把它的方向键导航弄死** ✗（`onMenuKeyDown` 靠 `document.activeElement` 找下标 ✓，焦点不在触发按钮上就收不到键 ✓）。所以 `.36` 撤掉 ✓，并留一条用例盯着"**打开菜单后不动焦点**" ✓（防止以后又去抢 ✓）。
  **教训**：别人的插件修好之后，自己的"绕过/对抗"要**跟着撤** ✗ —— 否则两边的修法会互相打架 ✓。
- **命令发出后要在地址栏留住** ✓（2026-10-29 用户要求 ✓）：命令**不是地方** ✓ —— 菜单是瞬时浮层 ✓，feed 下一刻就给出裸 `#/power` ✓，读者根本来不及看清自己粘的那条 ✓。做法 ✓：`driveTypedFragment` 里若 fragment 是**显式动作** ✓ → `holdCommand(fragment)` ✓（`COMMAND_STICKY_MS = 10000` ✓）；地址栏的 `show()` 里 `heldCommand(Date.now())` 非空就用它 ✓。**上限 10 秒** ✓：够应用退出 ✓，而**命令失败时也不会让地址栏一直说谎** ✓。
  ⇒ **第一次没生效** ✓（用户截图：遮罩在 ✓ 但地址栏是屏幕路由 ✗）：真正的写入者是**回车后的 `settle()`** ✗ —— 命令"立刻算落地" ✓ → 那条 `setTimeout` 里 `input.value = readableFragment(window.location?.hash)` ✓ 把留住的东西**自己抹掉** ✓✓✓。所以做法改成 ✓：地址栏的**所有**写入点收拢到 **`showFragment()`** ✓（它在留住期内不动 ✓），只有 `settle` ✓ / `Esc` ✓ / 粘了个解析不出的东西 ✓ / 点最近列表 ✓ 走它 ✓；**换成别的导航或按 Esc 会 `releaseCommand()`** ✓（留住不是枷锁 ✓）。
  ⇒ 这条**单测抓不住** ✗（假 DOM 里 `arrived()` 那条路走不到 ✓ —— 写了两版用例都是空转的 ✓，都删了 ✓）。验证靠**观察器**新记的地址栏 `value` ✓（`dev/inspect` ✓，只读 ✓）→ 从日志里看它有没有留住 ✓。
- **跑之前拿地址栏对一次，但只拒绝"写着另一个动作"** ✓（2026-10-29 ✓）：判据是 `typed.kind === 'power' && typed.id !== '' && typed.id !== link.id` ✓ —— **不能**要求"地址栏必须写着这个动作" ✗：菜单一开 ✓，屏上的 canonical 就是 `#/power` ✓（裸的 ✓），严格版会把**我们自己刚打开的菜单**当成 claim 过期 ✓ → 拒绝 ✓ → 读者要**按两次回车** ✓（用户实测 ✓）。现在：claim `restart` + 地址栏 `shutdown` → **仍然拒绝** ✓（这才是"要重启却关机"那条要防的 ✓）；claim `restart` + 地址栏 `#/power` 或别的界面 → **放行** ✓（那是菜单自己的状态 ✓ 或菜单已关 ✓）。用例：`… is not refused by the bar showing its own menu` ✓ 与 `… is still refused when the bar names another action` ✓。
